# FaceCat 项目深度分析与精修方案

> 版本：2026-05-23  
> 用途：后续精修 FaceCat 的主参考文档。所有 agent、计划和技术实现应优先对齐本文，再对齐 `PLAN.md` 和 `docs/技术方案.md`。

## 1. 总体判断

FaceCat 当前是一个可运行的多轨分析原型，已经具备面部 AU、头部姿态、AU 时间线、rPPG 生理信号、情绪弱推断、不一致性线索、基础标注和 JSON/CSV 导出能力。

但它还不是完整的面部行为标注工作台。当前缺口集中在产品闭环层：

- 项目文件格式还没有落地。
- 视频质量门控缺失。
- 候选短时事件检测缺失。
- 自动结果和人工确认没有完全分离。
- 语音/语言轨未进入离线批处理和 UI。
- 导出 schema 还没有覆盖 quality、event、cue、analysis_run 等字段。
- 测试覆盖主要集中在 face 模块。

阶段定位：

```text
当前状态：可运行技术原型
目标状态：本地 AI 辅助面部行为标注 MVP
核心差距：质量门控 + 候选事件 + 项目文件 + 标注闭环
```

## 2. 业务架构

### 2.1 产品定位

FaceCat 是本地优先的 AI 辅助面部行为视频标注工具。它帮助研究者、用户测试团队、广告素材评估人员和行为分析人员从视频中快速发现、复核、标注和导出可观察行为线索。

FaceCat 输出证据，不输出高风险自动判断：

- 输出 AU、landmarks、head pose、rPPG、F0、文本线索。
- 输出候选事件和触发理由。
- 支持人工复核 onset/apex/offset。
- 导出结构化数据和报告。
- 不判断是否说谎。
- 不断言真实情绪或心理状态。

### 2.2 用户流程

目标用户流程应收敛为：

```text
导入视频
  -> 自动抽帧和特征提取
  -> 质量门控
  -> 生成候选短时事件
  -> 时间线复核
  -> 调整 onset/apex/offset
  -> 添加标签和备注
  -> 导出 JSON/CSV/报告
```

当前已经完成：

- 视频导入和抽帧分析。
- AU/头姿/生理信号展示。
- AU 时间线。
- 基础起止标注。
- JSON/CSV 导出。

尚未完成：

- 自动候选事件。
- 质量门控。
- 项目文件和分析运行记录。
- 报告生成。
- 多模态完整同步。

### 2.3 产品红线

FaceCat 不支持或不优先支持：

- 招聘、绩效、课堂监控中的情绪评分。
- 微表情测谎和审讯结论生成。
- 犯罪倾向、心理异常、服从度等自动判断。
- 未告知或无同意的隐蔽分析。
- 以情绪分类准确率作为第一版核心卖点。

业务成功标准不是“情绪识别多准”，而是：

- 能否减少人工搜片段和标注时间。
- 候选片段是否有可回放证据。
- 低质量视频是否能提示不可靠。
- 导出数据是否能进入用户已有工作流。

## 3. Agent 架构

### 3.1 当前决策

项目后续只保留 Codex agent 体系：

- `AGENTS.md` 是项目级总入口。
- `.codex/agents/` 保存专精角色。
- Claude 侧重复文件不再维护。

### 3.2 角色分工

| Agent | 职责 | 主要路径 |
|---|---|---|
| project-manager | 跟踪计划、判断优先级、同步完成度 | `PLAN.md`, `docs/` |
| developer | 跨模块集成、重构、代码审查、修 bug | 全仓库 |
| tester | 单元测试、集成测试、边界测试 | `core/**/tests` |
| face-engineer | MediaPipe、AU 映射、head pose | `core/face` |
| physio-engineer | rPPG、呼吸率、生理轨质量 | `core/physiological` |
| voice-engineer | F0、RMS、语速、jitter、shimmer | `core/voice` |
| nlp-engineer | Whisper、语言特征、疏离化检测 | `core/language` |
| frontend-dev | PySide6 UI、时间线、标注交互；后续本地服务 | `ui`, future `backend` |

### 3.3 Agent 协作规则

每个任务都应遵循：

1. 先读本文。
2. 再读 `PLAN.md` 和 `docs/技术方案.md`。
3. 最后读目标模块源码。
4. 修改后必须运行对应测试或至少 `py_compile`。
5. 完成后同步文档或计划状态。

### 3.4 当前 agent 技术债

需要修正并保持同步：

- `frontend-dev` 不能只写 FastAPI + 纯 HTML；当前主 UI 是 PySide6。
- `physio-engineer` 不能继续写胸腔/锁骨呼吸为已实现路径；当前实现是额头 ROI RGB 低频呼吸估计。
- `tester` 不能默认只跑根目录 `tests/`；当前测试位于 `core/face/tests`，未来应按模块放 `core/<module>/tests`。
- 所有 agent 应把候选事件、质量门控、项目文件作为后续精修主线。

## 4. 项目架构

当前项目结构清晰，适合继续演进：

```text
FaceCat/
  core/
    face/              # 面部特征
    physiological/     # rPPG / 呼吸
    voice/             # 语音韵律
    language/          # 转录和文本特征
    emotion/           # AU 弱情绪推断
    cue/               # 不一致性统计线索
    sync/              # snapshot 和导出
  ui/                  # PySide6 桌面 UI
  docs/                # 技术和项目文档
  .codex/agents/       # Codex agent 定义
```

结构优点：

- 每条轨道按领域拆包。
- face 模块抽象边界较清楚。
- UI 和核心算法目前仍可直接调试。
- 文档已明确产品边界和红线。

结构短板：

- 没有 `core/quality`。
- 没有 `core/events`。
- 没有项目文件/运行记录模块。
- `ui/main_window.py` 过大，承担过多职责。
- 没有依赖声明文件，如 `pyproject.toml` 或 `requirements.txt`。
- 没有 CI 和覆盖多模块的测试。

## 5. 软件架构

### 5.1 当前运行架构

当前是本地 PySide6 单体桌面架构：

```text
run_ui.py
  -> ui.MainWindow
    -> _CameraWorker(QThread)
      -> MediaPipeFaceAnalyzer
      -> MediaPipeBlendshapeLookupAU
      -> CHROMRPPG / POSRPPG
      -> BreathAnalyzer
    -> TimelineWidget
    -> EmotionInferrer
    -> DeceptionCueAnalyzer
    -> core.sync export
```

优点：

- 原型开发快。
- 本地隐私边界清楚。
- 摄像头和视频流程都能跑。
- UI 调试成本低。

问题：

- UI 直接调 core，后续项目文件和批处理会让 `MainWindow` 继续膨胀。
- 视频文件分析在 UI 线程中同步执行，长视频会阻塞界面。
- 摄像头 worker 中同时做采集、分析、rPPG、FPS 统计，职责偏重。
- snapshot 生成散落在 UI，未统一经过 `SnapshotBuilder`。

### 5.2 核心模块评估

| 模块 | 当前状态 | 判断 |
|---|---|---|
| `core/face` | 抽象和实现较完整，有测试 | 当前最稳 |
| `core/physiological` | 算法骨架完整，UI 已接入 | 缺测试和 fps 校准 |
| `core/voice` | 分析器可用 | 未接入视频抽音频和 UI |
| `core/language` | 转录和规则分析器可用 | 未接入批处理和 UI |
| `core/emotion` | AU 规则弱推断可用 | 需强调弱推断和测试 |
| `core/cue` | 9 个统计线索可用 | 需导出和测试 |
| `core/sync` | snapshot/export 基础可用 | schema 需要升级 |
| `ui` | 可演示 | 需要拆分和异步化 |

### 5.3 推荐目标架构

中期目标仍然可以保留 PySide6，但核心流程应从 UI 中抽出来：

```text
Application Service Layer
  ProjectService
  AnalysisRunService
  AnnotationService
  ExportService

Core Domain
  face
  physiological
  voice
  language
  emotion
  cue
  quality
  events
  sync

Infrastructure
  project.facecat file store
  JSON/CSV/HTML exporters
  MediaPipe model adapter

UI
  MainWindow
  VideoPanel
  TrackPanel
  TimelineWidget
  AnnotationPanel
```

## 6. 技术方案

### 6.1 数据模型

所有结果必须能回答四个问题：

1. 来自哪个视频。
2. 用哪个模型、参数和版本生成。
3. 是自动生成还是人工确认。
4. 质量和置信度如何。

核心实体：

| 实体 | 说明 |
|---|---|
| Project | 一个分析项目 |
| VideoAsset | 原始视频资产或引用 |
| AnalysisRun | 一次不可变分析运行 |
| FaceTrack | 人脸轨迹，MVP 可先单脸 |
| FrameObservation | 单帧特征 |
| QualityFrame | 单帧质量 |
| EventCandidate | 自动候选事件 |
| Annotation | 人工确认或修正 |
| ExportJob | 导出任务 |

### 6.2 项目文件格式

第一版落地 `project.facecat/` 文件夹格式：

```text
project.facecat/
  manifest.json
  assets/
    original.mp4
  runs/
    run_YYYYMMDD_HHMMSS/
      run.json
      features.csv
      quality.json
      events.json
      snapshots.json
  annotations/
    annotations.json
  exports/
    events.csv
    snapshots.csv
    report.html
```

约束：

- `runs/` 保存自动分析结果，不可变。
- `annotations/` 保存人工修改，不覆盖自动结果。
- `exports/` 可重新生成。
- 原始视频可复制，也可只记录引用路径。

### 6.3 质量门控

新增 `core/quality/`，输出：

- face detected confidence。
- face box size ratio。
- blur score。
- brightness / contrast。
- landmark availability。
- head pose extreme angle。
- frame drop / unstable fps。
- occlusion proxy。

用途：

- 时间线高亮低质量区间。
- 候选事件过滤。
- 报告中说明不可分析或低可信片段。

### 6.4 候选事件检测

新增 `core/events/`，第一版用可解释规则：

1. 对 AU/blendshape 曲线做平滑。
2. 计算局部 baseline。
3. 用 z-score 或差分检测短时显著变化。
4. 找 onset/apex/offset。
5. 用质量门控、头姿和持续时间约束过滤。
6. 合并相近候选。
7. 输出触发特征和质量标记。

事件 schema：

```json
{
  "event_id": "evt_001",
  "video_id": "video_001",
  "track_id": "face_1",
  "analysis_run_id": "run_20260523_001",
  "onset_ms": 12340,
  "apex_ms": 12480,
  "offset_ms": 12620,
  "confidence": 0.72,
  "source": "rule_change_point_v1",
  "trigger_features": ["AU12", "AU6"],
  "quality_flags": ["stable_head_pose"],
  "status": "candidate"
}
```

### 6.5 导出和报告

MVP 导出：

- `snapshots.json`：帧级完整数据。
- `snapshots.csv`：宽表，适合统计分析。
- `events.json`：候选和人工确认事件。
- `events.csv`：事件表。
- `report.html`：方法、参数、质量、候选、人工确认、限制声明。

导出必须区分：

- 自动候选。
- 人工确认。
- 模型版本。
- 质量限制。
- 是否包含原始图像或片段。

## 7. 完成度评估

| 维度 | 完成度 | 说明 |
|---|---:|---|
| 面部轨 | 85% | 核心可用，有测试；缺质量和多脸 |
| 桌面 UI | 65% | 可演示；主窗口过大，视频分析阻塞 |
| 时间线 | 60% | AU 波形可用；缺事件区间和质量层 |
| 生理轨 | 45% | 算法接入 UI；缺测试和校准 |
| 语音轨 | 30% | 分析器有了；未接入视频和 UI |
| 语言轨 | 30% | 转录和规则有了；未接入批处理 |
| 情绪/线索 | 55% | UI 已显示；需测试和导出 |
| 标注/导出 | 35% | 基础可用；缺项目结构和报告 |
| 工程化 | 40% | 仓库清楚；缺依赖、CI、广泛测试 |

整体完成度约 50%-55%。它已经是可演示原型，但离可试点 MVP 还差 3-4 个关键模块。

## 8. 主要风险

### 8.1 产品风险

- 用户误解为测谎或情绪识别工具。
- 候选事件误报过多，反而增加标注负担。
- 没有质量门控时，低质量视频容易产生错误自信。

### 8.2 技术风险

- rPPG 对光照、运动、fps 非常敏感。
- MediaPipe blendshape 到 FACS AU 是近似映射，不是正式 AU 模型。
- 语音和语言轨如果不做时间同步，导出价值有限。
- `MainWindow` 继续膨胀会拖慢后续开发。

### 8.3 工程风险

- 没有依赖锁定，环境可复现性不足。
- 测试覆盖不均衡。
- 没有 golden set，算法变化缺少回归标准。
- agent 文档若不持续同步，会误导后续开发。

## 9. 精修路线图

### P0：文档和 agent 收敛

- 新增本文作为精修主文档。
- 删除 Claude 侧重复 agent。
- Codex agent 全部指向本文。
- 更新 README、PLAN、AGENTS 的文档入口。

### P1：工程基线

- 新增 `pyproject.toml`，统一基础、开发、语音、语言依赖。
- 修正类型注解中 `X | None` 与项目规范的冲突。
- 清理节注释横幅或放宽规范。
- 建立模块测试入口。
- 为 physio、voice、language、emotion、cue 增加基础单测。

### P2：项目文件和 schema

- 实现 `core/project/`。
- 定义 `ProjectManifest`、`AnalysisRun`、`VideoAsset`。
- 统一 `SnapshotBuilder` 的生成入口。
- 导出 JSON/CSV 使用统一 schema。

### P3：质量门控

- 实现 `core/quality/`。
- 在视频分析结果中写入质量字段。
- UI 时间线显示低质量区间。
- 报告和导出包含质量说明。

### P4：候选事件

- 实现 `core/events/`。
- 基于 AU/blendshape 曲线生成候选事件。
- UI 显示候选区间。
- 支持人工确认、拒绝和调整边界。

### P5：多模态闭环

- 视频抽音频。
- 接入 `LibrosaVoiceAnalyzer`。
- 接入 `WhisperTranscriber` 和 `DetachmentAnalyzer`。
- 按 timestamp 合并到 snapshot。
- UI 增加语音/语言轨。

### P6：报告和试点

- 生成 HTML 报告。
- 建立 golden set。
- 统计候选召回、每分钟误报、标注节省时间。
- 找 3-5 个真实用户试用。

## 10. 下一步执行建议

下一步不要先大改 UI，也不要先训练模型。优先顺序应为：

1. 固化文档和 agent 体系。
2. 建立依赖和测试基线。
3. 落地项目文件格式。
4. 做质量门控。
5. 做候选事件 detector。

这样可以先把“原型”变成“可复现、可审计、可迭代”的工程基础，再逐步增强多模态和 UI。
